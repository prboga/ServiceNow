01
Overview

How SG-SCCM Works

SG-SCCM (Service Graph Connector for Microsoft SCCM) is a ServiceNow application (sn_sccm_integrate) that performs a one-directional, scheduled import of device and software data from Microsoft Configuration Manager's SQL Server database directly into the ServiceNow CMDB. SCCM is treated as an authoritative, read-only data source — the connector never writes back to SCCM.

Microsoft Configuration Manager (SCCM) discovers devices in the network (e.g., via Active Directory Forest Discovery) and stores all hardware inventory, software inventory, and network data in its SQL Server database. SG-SCCM reaches into that SQL Server database via a JDBC connection routed through a Windows-based MID Server, and ingests the data into CMDB tables.

sn_sccm_integrate — installed from the ServiceNow Store
🔗

JDBC connection to SCCM SQL Server database via Windows MID Server
📥

🧩

02
Trigger Lifecycle

What Happens When an Import Schedule Executes

When a Scheduled Data Import fires (either on its configured interval or manually via "Execute Now"), a precise sequence of events unfolds inside ServiceNow before any data ever leaves the SCCM database.

🕐
Step 1 — Scheduler triggers the job
ServiceNow's job scheduler fires the Scheduled Data Import record (stored in sys_trigger). The parent job (Computer Identity) executes first; all child jobs are queued to run only after the parent completes.
🔄
Step 2 — SQL Statement is refreshed from the Instance record
The job reads the Custom SQL Statement field from the corresponding record in the sn_sccm_integrate_instance table and copies it into the sql_statement field of the Data Source record (sys_data_source). This is a critical design decision: SQL is managed in the instance table, not in the data source directly.
📋
Step 3 — Data Source configuration is resolved
The job reads the full Data Source record: JDBC connection alias, MID Server assignment, import set table name (staging table), and the now-updated SQL statement.
📤
Step 4 — ECC Queue output record is created
ServiceNow creates an output record in the ecc_queue table addressed to the designated MID Server with topic JDBCProbe, containing the full connection and SQL payload as XML.
🖥️
Step 5 — MID Server executes the query and returns results
The MID Server picks up the output record, executes the SQL against the SCCM SQL Server database via JDBC, and sends results back as input records in the ECC queue.
🗃️
Step 6 — Import Set Sensor populates the staging table
ServiceNow processes the ECC input record XML, inserts rows into the staging (import set) table, then the Robust Transform Engine transforms the staged rows into CMDB records via IRE.
⚠️
Important: Never modify the SQL Statement directly on the Data Source record. Because each time the Scheduled Data Import runs, it overwrites the Data Source SQL from the sn_sccm_integrate_instance table. Always make SQL changes in the SCCM Instances table under the Custom SQL Statement field.
03
Configuration Linkage

How the Data Source is Linked to the Import Schedule

The Scheduled Data Import record and the Data Source record are explicitly linked: the Scheduled Data Import record has a reference field pointing to the Data Source (sys_data_source). The Data Source, in turn, holds the JDBC connection alias, staging table name, MID Server reference, and SQL query.

Scheduled Data Import table
sys_import_schedule
Data Source table
sys_data_source
SCCM Instance config table
sn_sccm_integrate_instance
Connection & Credential alias
sys_alias (SCCM JDBC Connection Credentials)

What kicks off the process? The sys_trigger scheduler fires the Scheduled Data Import job at the configured interval. This job reads its linked Data Source record to get the JDBC connection details and SQL statement. It then programmatically calls the ServiceNow Import Set loading engine, which builds the ECC queue output record targeting the MID Server defined in the Data Source.

For delta (incremental) imports, the SQL statement uses the last_run_datetime field from the Data Source record as a filter parameter — pulling only records modified after the last successful run.

🔗
The Connection Name you set during Guided Setup (e.g., "USA") becomes a prefix for all created Data Sources and Scheduled Imports (e.g., USA-SG-SCCM Computer Identity). This naming allows multi-instance SCCM setups — each SCCM environment gets its own isolated set of data sources and import schedules under a child Connection & Credential alias.
04
ECC Queue

How an Output Record is Created in the ECC Queue

The ECC (External Communication Channel) Queue (ecc_queue) is the central message bus between the ServiceNow instance and MID Servers. It holds two types of records: output records (instructions from SN to MID) and input records (responses from MID to SN).

When the Import Set loading engine resolves a JDBC-type Data Source, it creates an output record in the ecc_queue table with the following key fields:

ECC Queue FieldValue SetPurpose
agentmid.server.<MID_Name>Identifies which MID Server should process this record
topicJDBCProbeTells the MID Server which Java probe handler to invoke
queueoutputMarks this as a command going TO the MID Server
statereadySignals the MID Server this record is ready for pickup
payloadXML with JDBC details + SQLContains the full instruction set for the JDBC probe
agent_correlatorSys_id of the data source jobUsed to trace output back to the originating feature/job
nameDescriptive labelHuman-readable identifier for the probe

The XML payload inside the ECC queue output record looks structurally like this:

XML — ECC Queue Output Payload (JDBCProbe)
<parameters>
  <parameter name="driver"
    value="com.microsoft.sqlserver.jdbc.SQLServerDriver"/>
  <parameter name="driver_jar"
    value="mssql-jdbc.jar"/>
  <parameter name="url"
    value="jdbc:sqlserver://<sccm_host>;databaseName=CM_<SiteCode>"/>
  <parameter name="query" value="Specific SQL"/>
  <parameter name="sql_statement"
    value="SELECT v_R_System.ResourceID, v_R_System.Name0,
      v_GS_COMPUTER_SYSTEM.Manufacturer00, v_GS_COMPUTER_SYSTEM.Model00,
      v_GS_PC_BIOS.SerialNumber00, WorkstationStatus_DATA.LastHWScan
      FROM v_R_System
      JOIN v_GS_COMPUTER_SYSTEM ON ...
      WHERE WorkstationStatus_DATA.LastHWScan > @lastrun"/>
  <parameter name="target_table"
    value="sn_sccm_integrate_sccm_2019_computer_id"/>
</parameters>
💡
AMB Notification: The moment the output record is inserted into ecc_queue, an Asynchronous Message Bus (AMB) message is immediately pushed to the MID Server's subscribed channel. This means the MID Server is notified in real-time rather than relying solely on polling.
05
MID Server Internals

How the MID Server Picks Up the Output Record

The MID Server is a Java application running on a server within the corporate network, maintaining an outbound HTTPS connection to the ServiceNow instance. It operates on a receive-then-poll model using AMB for near-real-time notification.

📡
AMB Notification Received
Upon the ECC output record insert, ServiceNow pushes an AMB message to the MID Server's channel. The MID Server receives this and immediately initiates a poll of the ecc_queue table for output records assigned to it in ready state.
📋
Poll for Ready Output Records
The MID Server queries: records where agent = 'mid.server.<name>', queue = 'output', state = 'ready'. Records are fetched oldest first, highest priority first. Only a certain number are fetched at once, proportional to the MID Server's configured thread count. On startup, it also re-fetches records in processing state (assuming previous death mid-execution).
📢
Notify the Instance — "Queue Processing"
The MID Server writes a topic=queue.processing record back to the instance, signalling that it has acknowledged the job. The output record state transitions from ready → processing.
🧵
Internal Worker Thread Queue
The accepted record is placed into the MID Server's internal in-memory queue. A free Worker Thread from the thread pool picks it up. The thread pool used (High, Low, etc.) depends on the record's priority. An output record in "processing" state does NOT necessarily mean it's actively running — it may still be waiting for a free thread.
🔌
JDBCProbe Java Code Invoked
The Worker Thread passes the work to the Java probe class registered for the JDBCProbe topic. This class parses the XML payload from the ECC record and executes the JDBC query. Agent log entries contain the sys_id of the ECC output record for traceability.
06
JDBC Execution

How SQL Statements are Executed on the MID Server

The MID Server's JDBCProbe Java class handles all the mechanics of connecting to the external SQL Server and executing the query. Here's the precise sequence:

  • 1
    Parse XML Payload: The JDBCProbe class extracts the JDBC driver class name, driver JAR path, connection URL (with host, port, database name), credentials, query type, and the SQL statement string from the ECC queue payload XML.
  • 2
    Load JDBC Driver: The MID Server dynamically loads the SQL Server JDBC driver (com.microsoft.sqlserver.jdbc.SQLServerDriver) from its local JAR repository. Windows Integrated Authentication (NTLM/Kerberos) or SQL auth is used based on configuration.
  • 3
    Establish JDBC Connection: A DriverManager.getConnection(url, user, password) call opens a JDBC connection from the MID Server host to the SCCM SQL Server. Since the MID Server is a Windows machine on the same domain, it can use Integrated (Windows) Authentication without a username/password if configured.
  • 4
    Prepare and Execute SQL: A JDBC Statement or PreparedStatement is created and the SQL query is executed via executeQuery(). The SQL Server account used must have the db_datareader role on the SCCM database.
  • 5
    Iterate ResultSet: The returned ResultSet is iterated row by row. The MID Server buffers rows into chunks based on the configured result set size (controlled by jdbcprobe_result_set_rows, default varies).
  • 6
    Format as XML: Each chunk of rows is serialized into an XML document where column names become element names and row values become element content.
  • 7
    Close Resources: The ResultSet, Statement, and Connection are closed. The MID Server logs the completion with probe time and result row count.
XML — ECC Input Payload (JDBC Result from MID)
<results probe_time="4832" result_code="0">
  <result>
    <row num="1">
      <ResourceID>16777217</ResourceID>
      <Name0>WORKSTATION-01</Name0>
      <Manufacturer00>Dell Inc.</Manufacturer00>
      <Model00>Latitude 5520</Model00>
      <SerialNumber00>ABC1234XYZ</SerialNumber00>
      <LastHWScan>2025-06-07 03:12:44.000</LastHWScan>
    </row>
    <row num="2"> ... next row ... </row>
  </result>
  <parameters>
    <parameter name="agent" value="mid.server.WIN-SCCM-MID"/>
  </parameters>
</results>
07
Batching Strategy

Single SQL Execution vs. Batch Record Processing

✅
The SQL statement is executed ONCE as a single query. The MID Server does not re-execute the SQL per batch. Instead, it iterates the returned ResultSet and divides the results into multiple chunks — each chunk becomes a separate ECC queue input record sent back to ServiceNow.

Here is how batching works at each layer of the pipeline:

LayerMechanismDefault / Config
JDBC ResultSet chunking
(MID Server)		 The MID Server reads the JDBC ResultSet and groups rows into payload chunks before sending each chunk as a separate ECC input record. Controlled by the jdbcprobe_result_set_rows field on the Data Source record. 200 rows/chunk default
ECC payload size limit
(MID Server → SN)		 Each ECC input record payload must stay under the max payload size. If a chunk is too large, the row count per chunk must be reduced. Controlled by system property mid.eccq.max_payload_size. Configurable
Import Set batch processing
(ServiceNow)		 When ServiceNow processes the staging table rows, it uses batch transactions. glide.import_set_load_usebatch and glide.import_set_load_batch_size control how many rows are committed per transaction. A single Import Set record is created, but internally data is committed in batches. 1000 rows/batch default
📊
The commonly referenced "1500 records" batch size is not a hard-coded OOTB default in the core platform — it may refer to a custom configuration set in specific environments. The platform defaults are 200 rows per JDBC result chunk and 1000 rows per import set batch transaction. Both can be tuned for your dataset size.
08
MID Server Storage

Where Output is Stored on the MID Server

After the JDBCProbe executes the SQL and serializes the results into XML, the MID Server does not hold the data in memory and immediately fire it to ServiceNow in a single step. Instead, it uses a local disk-based queue to manage sending reliability and ordering.

📁
ECC Sender Folder
Result XML files are written to the MID Server's local ECC Sender queue directory on disk (typically within the agent's work directory). Files are named using the ECC output record's sys_id.
📬
ECCSender Component
The ECCSender monitor on the MID Server reads XML files from the local queue folder and sends them to ServiceNow in priority order, serially (not in parallel). This serialized sending is why latency increases when many probes pile up.
🔒
Durability
Because results are persisted on disk before sending, the MID Server can survive a transient network outage and resume sending when connectivity is restored.
🗂️
Multiple Chunks
If a query returns 10,000 rows at 200 rows/chunk, the MID Server creates ~50 separate XML files in the local queue, each destined to become one ECC input record in ServiceNow.
🔍
Tracing in agent logs: Every MID Server log entry related to a probe contains the sys_id of the ECC output record. You can search logs/agent0.log.* for the ECC output sys_id to find all traffic (pickup time, execution time, send time) for a given probe run.
09
Return Path

How Results are Sent Back to ECC Queue as Input Records

The ECCSender component on the MID Server sends each XML result file to ServiceNow, inserting it as an input record in the ecc_queue table. This is the return path.

📂
ECCSender reads local XML files
ECCSender scans the local ECC queue folder in priority order and picks up the result XML files written by the JDBCProbe worker thread.
📤
Insert ECC Input Record
For each XML file, ECCSender inserts an input record into the ecc_queue table on the ServiceNow instance. Key fields: queue=input, state=ready, topic=JDBCProbe, name matches the original output record name. The payload contains the XML result rows.
✅
Output Record Marked "Processed"
When ServiceNow receives the input and sees the matching output record, a Business Rule updates the original output record state to processed and records the "Processed" timestamp.
⏰
Sensor Job Scheduled (sys_trigger)
The arrival of the ECC input record triggers scheduling of an asynchronous sensor job (sys_trigger). This sensor job will process the XML payload and populate the staging table. Multiple input records (one per chunk) each create their own sensor job execution.
⏱️
Timing Anatomy:
  • Enqueued → Output record inserted, state = ready
  • Processed time → State changes to "processing" (MID picked it up; note: confusingly named)
  • Updated time → Input record received back; state = processed (actual completion)

Long gaps between "processed" and "updated" indicate MID Server is busy processing other probes or experiencing network latency sending results back.
10
Staging Layer

How ServiceNow Processes ECC Input and Populates the Staging Table

When the sensor job fires, it processes the XML payload from the ECC input record and writes the data into the Import Set staging table — a temporary table that extends sys_import_set_row. Each SG-SCCM data source has its own dedicated staging table (e.g., u_imp_sccm_computer_identity).

  • 1
    ECC Input Sensor fires: The asynchronous sensor job reads the ECC input record payload (XML with JDBC result rows).
  • 2
    XML Parsed row-by-row: Each <row> element in the XML is parsed. Column names map to staging table field names. Values are extracted and typed appropriately.
  • 3
    Rows inserted into staging table: Each parsed row is inserted as a new record in the Import Set staging table. The record's sys_import_set field links it to the current Import Set run. Initial state: Pending.
  • 4
    Multiple ECC inputs = multiple sensor runs: Because large result sets produce multiple ECC input chunks, multiple sensor job executions run (potentially in parallel). All write to the same Import Set staging table run.
  • 5
    Import Set record state tracks progress: The sys_import_set record transitions: Loading → Loaded (once all rows are in). Then transformation begins.
  • 6
    Pre-import script runs (optional): If a pre-import script is configured on the Data Source, it runs once data is successfully loaded into the staging table (best practice: use onStart hook).
🗄️
Staging Table Housekeeping: ServiceNow automatically purges Import Set staging table rows older than 7 days via the "Import Set Deleter" scheduled job. This keeps staging tables from growing unbounded. Only the most recent import run's data is needed for transformation.
11
Transform Engine

How RTE and ETL Come Into the Picture

Once all rows are loaded into the staging table, the transformation phase begins. SG-SCCM uses Robust Import Set Transformers — not legacy Transform Maps — for all its core import jobs (the exception being software usage and edition jobs, which still use classic Transform Maps).

Each active SG-SCCM Scheduled Import has a corresponding Robust Import Set Transformer record in the sys_robust_import_set_transformer_list table. This record creates a one-to-one mapping between the staging table and the Transformer Definition (ETL Definition) that governs the transformation logic.

🔀
Robust Transform Engine (RTE)
Orchestrates transformation of raw staging rows into structured IRE payloads. Uses ETL definitions authored in IntegrationHub ETL.
🏗️
IntegrationHub ETL
The UI and metadata layer. Defines Entities, Mappings, Operations, and Conditional Scripts that RTE executes.
🧹
Cleanse Transforms
Scripts like CleansModelAndCompany normalize manufacturer and model names by looking them up in the Hardware Model table, returning a model_id.
🔍
Lookup Operations
Resolve reference fields: e.g., map the SCCM LastHWScan value to the CI's last_discovered field, or map a username to a sys_user sys_id.
📊
RTE reads Staging Table Rows
RTE iterates through rows in the staging table with state = Pending. For each row, it loads the matching ETL/Transformer Definition.
⚙️
ETL Transforms Applied Per Row
For each staging row, ETL operations are applied in order: field extraction, data cleansing (normalizing manufacturer/model), lookup (resolving user/IP references), conditional logic (e.g., classifying as Computer vs. Windows Server based on system role), and field mapping to target CI class fields.
📦
IRE Payload Assembled
RTE assembles a structured IRE payload for each row. This payload includes the CI class, all attribute key-value pairs, the discovery source (SG-SCCM), and any related item payloads (e.g., serial number records, IP addresses for network import).
🏷️
Staging Row Marked "Processed"
After a staging row's IRE payload is successfully submitted, its state is updated to Processed in the import set table. Failed rows are marked Error with a message.
12
CMDB Ingestion

How ETL Generates the IRE Payload and Passes It to IRE

The Identification and Reconciliation Engine (IRE) is the gatekeeper of the CMDB. Rather than writing directly to CMDB tables, all SG-SCCM data passes through IRE — ensuring deduplication, reconciliation between multiple discovery sources, and CMDB health.

📦
IRE Payload Structure
The ETL-generated IRE payload is a structured JSON/object containing: CI class (e.g., cmdb_ci_win_server), attribute map (field name → value pairs), discovery source (SG-SCCM), and lookup fields (the identification attributes like serial number, resource ID). Related items (serial numbers, IPs) are nested sub-payloads.
🔍
IRE — Identification Phase
IRE applies Identification Rules configured for the CI class. For Computer CIs, it checks attributes like hostname, serial number, and SCCM ResourceID against existing CMDB records to determine if a match exists. IRE uses a ranked list of identification rules — if a high-confidence rule matches (e.g., serial number match), it uses that CI. If no match, a new CI is created.
⚖️
IRE — Reconciliation Phase
If a matching CI is found, IRE applies Reconciliation Rules. These rules define which discovery source has higher priority for each field. If SG-SCCM is set to lower priority than ServiceNow ITOM Discovery for a given field, IRE will reject SG-SCCM's proposed value and preserve the higher-priority source's value. Rejected values are visible in CMDB 360 as "Proposed Values".
🗄️
CMDB Tables Updated
After identification and reconciliation, IRE performs the actual database writes: INSERT for new CIs or UPDATE for existing ones, directly into the target CMDB table. Related items (disks, NICs, serial numbers, IP addresses) are also upserted into their respective tables and linked via relationship records.
🔄
Partial Payloads (Edge Case)
If IRE cannot fully process a payload due to a missing referenced CI (e.g., a software install record references a computer CI that hasn't been created yet), the payload is stored in the CMDB IRE Partial Payloads table for retry processing once the dependency is resolved.
🛡️
IRE Data Source Rules (Optional)
Administrators can configure IRE Data Source Rules to restrict what SG-SCCM can do: e.g., "Insert Not Allowed" prevents SG-SCCM from creating new Computer CIs (only update existing ones found by Discovery). This prevents unwanted CI creation from SCCM-only devices.
🌐
CMDB 360 / Multisource CMDB: Enabling glide.identification_engine.multisource_enabled = true unlocks visibility into multi-source reconciliation. Administrators can see which discovery source "won" each field, view proposed values from lower-priority sources, and understand exactly why a field was or wasn't updated by SG-SCCM.

Summary of the complete data journey: A device in SCCM's SQL Server database — discovered by Active Directory Forest Discovery — travels through a Scheduled Data Import trigger, through a JDBC connection on the MID Server, through the ECC Queue as output and input records, into a staging table via an import set sensor, through RTE/ETL transformation and cleansing, through IRE identification and reconciliation, and finally lands as a cmdb_ci_win_server or cmdb_ci_computer record in the ServiceNow CMDB — with serial numbers, network adapters, IPs, disk drives, and software installations all linked as related records.
