ServiceNow Identification & Reconciliation Engine

A complete walkthrough of how every incoming payload is validated, identified, reconciled, and committed to the CMDB — across 8 sequential phases with exactly 3 possible outcomes.

✓ Successful Commit
⏳ Partial Payload Stored
✕ Incomplete — Dead Letter Queue
Section 01

What is the IRE?

The ServiceNow CMDB is your organisation's master inventory of every IT asset — servers, laptops, applications, network devices, and more. Data about these assets flows in continuously from multiple tools. The problem: when multiple tools report on the same laptop, they can conflict. One might create a duplicate record. Another might overwrite good data with stale information. A third might try to move a server into the wrong category.

The IRE (Identification & Reconciliation Engine) is the intelligent processing pipeline that sits between all incoming data and the CMDB. Every piece of incoming data — called a payload — must pass through the IRE before it can touch the database.

The Airport Analogy

Think of it like smart border control at an airport. Every passenger (payload) arrives, goes through passport control (identity check), customs inspection (rule evaluation), and is either admitted, held for further checks, or turned away — with a full record of why.

Core Purpose

  • Prevent duplicates — identify whether a CI already exists before creating a new one
  • Control who can update what — only authorised sources can modify specific fields
  • Handle missing dependencies — wait for related CIs to arrive before processing
  • Manage reclassification — safely change a CI's class when its type changes
  • Provide a full audit trail — every decision is logged with full detail

The 3 Things That Can Happen to Every Payload

Every payload that enters IRE will end in exactly one of three states — no exceptions:

✅ Successful Commit

All 8 phases completed. The CI has been created or updated in the CMDB.

⏳ Partial — Awaiting

Payload is held for up to 90 days, waiting for a dependency or an authorised source to create the CI first.

❌ Dead Letter Queue

Fatal validation error. Payload cannot be processed automatically. Requires manual investigation.

Section 02

The Big Picture

Before a payload reaches Phase 1, it must come from a recognised source. IRE accepts payloads from five integration types — each with a different method of sending data.

🔌
Service Graph Connectors
Pre-built certified connectors for third-party tools (SCCM, Intune, VMware, AWS, Azure). ServiceNow's recommended integration method.
🔍
Discovery
ServiceNow's built-in network scanner. Probes devices and maps their properties automatically.
📥
Import Sets
Structured bulk imports (CSV, spreadsheet, database) processed via IntegrationHub ETL.
⚙️
IntegrationHub ETL
Transformation and mapping layer for processing external data before it enters IRE.
🔗
Integrations
Any other source invoking the IRE API directly — custom integrations, REST API calls, or bespoke tools.
⚠️ Critical — Architects & Admins: The IRE Bypass Risk

Integrations that do NOT use Service Graph Connectors or IntegrationHub ETL — such as direct table inserts via scripts or legacy Transform Maps — bypass IRE entirely. They skip all 8 phases: no duplicate checking, no reconciliation rules, no source firewall. This is a significant data quality and governance risk. Audit every integration writing to CMDB tables.

The 8-Phase Journey

Every accepted payload travels through up to 8 sequential phases before it reaches a final state. The phases are not all mandatory — fast-pass (Phase 4) can skip Phase 5, and a blocked insert (Phase 2) routes to the partial table rather than continuing forward. The pipeline is intelligent, not linear.

Section 03

Phase-by-Phase Breakdown

Each phase card below can be expanded for full detail. Click any phase header to open it.

1
Structural Validation & Class Discovery
"Is this payload even valid enough to process?"
+

Before IRE does anything else, it verifies the incoming data makes sense. Think of it as checking that a form has been filled in correctly before processing it. If the form is illegible or references something that doesn't exist, you reject it immediately.

  1. Parse JSON Payload — the raw incoming data is read
  2. Validate JSON Structure — confirms the data is properly formatted JSON
  3. Validate Class Exists — confirms the CI class in the payload (e.g. cmdb_ci_windows_server) exists in ServiceNow's schema, checked against sys_db_object
  4. Discover Class Hierarchy — maps where this class sits in the CMDB class tree (e.g. Windows Server → Server → Hardware → CI)
  5. Validate Mandatory Fields — checks required fields are present, as defined in sys_dictionary
⬦ Decision Point — Validation Passed?
YES → Proceed to Phase 2
NO → Payload is immediately routed to the Dead Letter Queue (DLQ) — cmdb_ire_incomplete_payloads. Processing ends.

What Gets Stored in the DLQ

The DLQ captures everything needed for investigation: Raw Payload · Error Details · Stack Trace · Source Info · Received Timestamp. Nothing is silently lost.

Why This Matters

Failing fast here prevents bad data from ever reaching the CMDB. The DLQ ensures every failed payload is held for review. If your DLQ is growing, an integration is sending malformed payloads or referencing a CI class that does not exist in this environment.

▸ Tables Involved
sys_db_object sys_dictionary cmdb_ire_incomplete_payloads

sys_db_object — class registry (validates the class name exists)
sys_dictionary — mandatory field definitions per class
cmdb_ire_incomplete_payloads — the Dead Letter Queue

2
Data Source Rule — Firewall Check
"Is this source allowed to create new CIs for this class?"
+

Phase 2 consults the cmdb_ire_data_source_rule table to determine whether the incoming source is permitted to insert new CI records for the target class. Each rule is defined for a specific Data Source + CI Class combination and contains a single control: the "Insert not allowed" checkbox. This is the only control available — it governs new record creation only.

SettingBehaviour
Insert not allowed — unchecked (default / no rule)Source is permitted to insert new CIs for this class
Insert not allowed — checkedSource cannot create new CI records for this class
Important — One Rule Per Pair

Only one active rule can exist per Data Source + CI Class combination. The rule controls insert only. Whether a source can update existing CIs is handled by Reconciliation Rules in Phase 6, not here.

What Actually Happens When Insertion Is Blocked

This is where real-world behaviour differs from what you might expect. When IRE detects INSERT_NOT_ALLOWED_FOR_SOURCE, the payload is not immediately rejected and does not appear in cmdb_ire_output_target_item. Instead, the entire payload — including the blocked CI and every dependent CI in the same dependency graph — is stored in cmdb_ire_partial_payloads with the reason code embedded in the payload metadata.

Why the Payload Goes to Partial — Not Rejected

A source blocked from inserting a CI is typically still trusted to update that CI once it exists. IRE holds the payload in a "pending" state. When an authorised source later creates the CI, the partial is retrieved, merged, and reprocessed — this time as an update, which the original source is permitted to perform.

Example — What This Looks Like in Practice

A Service Graph Connector for SCCM sends a payload containing a cmdb_ci_computer (blocked), a cmdb_ci_disk (not blocked but depends on the computer), serial numbers, software installs, and key-value records. The entire payload is held together in cmdb_ire_partial_payloads. The computer record carries the INSERT_NOT_ALLOWED_FOR_SOURCE reason. The disk and related records carry no reason of their own — they are caught in the dependency hold. Everything waits for Discovery to create the computer. Once created, IRE retrieves the partial, processes everything: the disk is linked, serial numbers created, software recorded, and SCCM's attributes are updated.

Monitoring Note

Because INSERT_NOT_ALLOWED payloads go to cmdb_ire_partial_payloads — not to cmdb_ire_output_target_item — they will not appear in standard IRE output reports. Monitor the partial payloads table directly. A growing volume of records with INSERT_NOT_ALLOWED_FOR_SOURCE reason codes signals a source regularly arriving before an authorised source has created the parent CI.

▸ Tables Involved
cmdb_ire_data_source_rule cmdb_ire_partial_payloads

cmdb_ire_data_source_rule — the rule configuration (Data Source + CI Class + Insert not allowed checkbox)
cmdb_ire_partial_payloads — stores the held payload with INSERT_NOT_ALLOWED_FOR_SOURCE reason embedded

3
Partial Payload Recovery — Dependency Lookup
"Does this CI need another CI to exist first?"
+

Some CIs cannot exist in isolation. A network adapter belongs to a server. A software installation belongs to a computer. The parent or related CI must exist in the CMDB before IRE can properly process and link the child CI. Phase 3 handles this dependency problem gracefully — through three distinct paths.

🔴 Path A — Missing Dependencies Found
  1. IRE detects the payload references a CI that does not yet exist in the CMDB
  2. A Payload Hash is generated (Class + Source + Key + Dependency Signature)
  3. An index record is inserted into cmdb_ire_partial_payloads_index
  4. The raw JSON payload is compressed and stored in cmdb_ire_partial_payloads
  5. The payload is marked Awaiting Dependency with a 90-day TTL
  6. Processing ends — but this is not an error. The payload will be recovered automatically

After 90 days with no resolution, the partial payload is automatically purged.

🟡 Path B — No Missing Dependencies, But Previous Partials Exist
  1. IRE finds cached partial payloads that match this incoming payload's fingerprint
  2. Matching index records are retrieved from cmdb_ire_partial_payloads_index
  3. Cached payload(s) are loaded from cmdb_ire_partial_payloads
  4. The cached payload is merged with the incoming payload in memory
  5. Dependencies are resolved and a complete dependency graph is rebuilt
  6. Both the index record and cached payload are deleted from their tables
  7. Processing continues as a unified, complete payload → Phase 4
🟢 Path C — No Missing Dependencies, No Cached Partials

No dependency issues. Processing continues directly to Phase 4.

Why This Matters

Without Phase 3, dependent CIs would fail every time they arrived before their parent. Phase 3 turns IRE from a binary pass/fail gate into a smart holding system that can self-recover when the missing piece eventually arrives from any source.

▸ Tables Involved
cmdb_ire_partial_payloads_index cmdb_ire_partial_payloads

cmdb_ire_partial_payloads_index — lightweight lookup index (fast fingerprint matching)
cmdb_ire_partial_payloads — compressed raw JSON payload storage with metadata and 90-day TTL

4
Fast-Pass Identity Resolution
"Have we seen this CI from this source before? If so, take the shortcut."
+

Once a CI has been successfully identified and committed at least once, IRE records the relationship between the source and that CI in a register. Next time the same source sends data about the same CI, IRE can skip the full rule evaluation and jump straight to reconciliation.

  1. IRE looks up sys_object_source using two keys: Source Name (e.g. "SG-SCCM") + Source Native Key (the unique ID the source uses for this item)
  2. Decision: Identity Found?
⬦ Decision Point — Identity Found?
YES → Fast-Pass: IRE immediately binds to the existing CI. Phase 5 is skipped entirely. Processing jumps to Phase 6 (Reconciliation).
NO → No prior record exists. Proceed to Phase 5 for full identifier rule evaluation.
Why This Matters — Performance

For large environments processing thousands of CI updates daily, the fast-pass is a major performance optimisation. If IRE already knows that "SG-SCCM native key XYZ" maps to CI record abc123, there is no need to run all identification queries again.

⚠️ Admins & Architects — The Stale Cache Risk

sys_object_source is a cache. If your identification rules change after initial population, existing entries may point to the wrong CI. The fast-pass continues routing using old results, bypassing new rules entirely. Review and clean up sys_object_source entries after significant identification rule changes or data migrations.

▸ Tables Involved
sys_object_source

sys_object_source — the identity register / fast-pass cache. Maps Source Name + Source Native Key → CMDB CI sys_id.

5
Identifier Rule Execution & Match Processing
"Is this a new CI, an existing one, or a duplicate?"
+

This is the heart of the identification engine. When no fast-pass match exists, IRE runs a prioritised series of identification queries to determine whether a matching CI already exists in the CMDB.

  1. Load Identifier Sets from cmdb_identifier — the rule containers per CI class
  2. Load Identifier Entries from cmdb_identifier_entry — individual attribute combinations, ordered by priority (lowest number = evaluated first)
  3. Load Related Entries from cmdb_related_entry — for dependent CIs, defines how the lookup includes the parent relationship
  4. Traverse the Class Hierarchy — IRE walks from the specific child class up to the root, collecting all applicable rules
  5. Execute Identification Queries — for each identifier entry in priority order, IRE queries the CMDB for a matching CI

Three Possible Results

ResultWhat Happens
0 Matches No MatchCreate a new CI in the CMDB. Processing continues to Phase 6.
1 Match Single MatchUpdate the existing CI. Processing continues to Phase 6.
2+ Matches Multi-MatchDuplicate Detected. An audit record is written to cmdb_duplicate_audit_result. A reconcile_duplicate_task is created for manual resolution. Processing ends — waiting for a human to resolve.

Example — How Priority Evaluation Works

For a cmdb_ci_computer, IRE might evaluate entries in this order:

  • Priority 90: product_instance_id → if a single match is found, done
  • Priority 100: serial_number + serial_number_type → if no match above, try this combination
  • Priority 200: serial_number alone → if no match above, try this
  • Priority 300: name → final fallback

The first priority level that returns exactly one result wins. If none return a match, a new CI is created.

💡 Good to Know — Inclusion Rules

You can optionally add Inclusion Rules to restrict which existing CIs are eligible for matching. For example, configure IRE to only consider CIs where operational_status = Operational — preventing a new active CI from being merged with a decommissioned record that shares the same serial number. There are no out-of-the-box inclusion rules; they are optional advanced configuration.

▸ Tables Involved
cmdb_identifier cmdb_identifier_entry cmdb_related_entry cmdb_duplicate_audit_result reconcile_duplicate_task
6
Reconciliation & Attribute Masking
"Which source gets to update which fields — and is their data still fresh?"
+

Having identified the CI, IRE now decides which data in the payload is actually allowed to be written. Multiple sources may be reporting on the same CI, and they do not all have equal authority over every field. Phase 6 enforces attribute ownership and data freshness.

  1. Load Reconciliation Rules from cmdb_reconciliation_rule — defines which source has authority over which fields, in what priority order
  2. Determine Attribute Ownership — for each field in the payload, IRE checks which source currently owns that field
  3. Check Last Update Tracking in cmdb_datasource_last_update — records which source last updated each CI attribute and when
  4. Field Level Masking — any field where the incoming source is NOT the authoritative owner is stripped out (masked). That update is blocked.
  5. Evaluate Staleness Override using cmdb_data_refresh_rule — if the authoritative source has not updated a field within a defined number of days, it is considered stale. A lower-priority source is then permitted to write to that field.
Why This Matters

Imagine SCCM and Intune both reporting on the same laptop. Without reconciliation rules, whichever runs last overwrites the other's data — even if its data is less accurate. Reconciliation declares: "SCCM owns the RAM field. Intune owns device compliance status. Discovery owns the IP address." Each source stays in its lane.

Static vs Dynamic Reconciliation Rules

Static Rules
A fixed priority list. Source A (priority 1) always wins over Source B (priority 2). Simple, predictable, and the most common type in use.
Dynamic Rules
The winner is decided by data characteristics: First Reported, Last Reported, Most Reported, Smallest / Largest Value. Dynamic rules take precedence over static rules when both apply to the same field.
Data Refresh Rules — Staleness

If the primary source hasn't updated a field within N days, it is treated as stale and a lower-priority source can step in. This prevents a failed or decommissioned integration from permanently locking a field it is no longer updating.

▸ Tables Involved
cmdb_reconciliation_rule cmdb_datasource_last_update cmdb_data_refresh_rule
7
Reclassification Matrix Processing
"Has this device's type changed — and is that safe to do automatically?"
+

Every CI in the CMDB has a class (type). If incoming data indicates the class should change — a generic "Server" record is now confirmed to be a "Linux Server" — that change needs to be evaluated before it happens. Phase 7 determines whether the reclassification is safe to apply automatically or requires human review.

  1. Compare Current Class vs Incoming Class — is the class in the payload different from what the CI currently holds?
  2. Determine Reclassification Type
  3. Evaluate Reclassification Restrictions — system properties control whether each type is permitted automatically

The Three Types of Reclassification

TypeDirectionExampleRisk
UpgradeMore specific classcmdb_ci_server → cmdb_ci_linux_serverLow — adds more detail
DowngradeLess specific classcmdb_ci_linux_server → cmdb_ci_serverHigh — loses Linux-specific attributes
HorizontalSame level, different branchcmdb_ci_linux_server → cmdb_ci_win_serverHigh — data loss possible
⬦ Decision Point — Reclassification Allowed?
YES → Proceed to Phase 8. The CI will be reclassified as part of the atomic commit.
NO → A reclassification_task record is created for manual approval. Processing ends — waiting for human review.
Why This Matters

Automatic reclassification can be destructive. Downgrading a cmdb_ci_linux_server to cmdb_ci_server strips away Linux-specific attributes. A conservative pattern: allow automatic upgrades, require human approval for downgrades and horizontal moves.

▸ Tables Involved
reclassification_task
8
Atomic Transaction Commit
"Save everything at once — or save nothing at all."
+

Phase 8 is where all decisions from every previous phase are executed against the database. The word atomic is the key concept: all changes succeed together, or all changes fail together. There is no partial write.

  1. Insert / Update CI in the target CMDB table (cmdb_ci_*) — the actual CI record is created or updated
  2. Update Relationships in cmdb_rel_ci — if the payload included relationship data, those connections are written
  3. Update Identity Register in sys_object_source — so the fast-pass shortcut (Phase 4) works correctly next time
  4. Update Source Tracking in cmdb_datasource_last_update — refreshes the last-updated timestamp for each attribute written
  5. Write Output Item to cmdb_ire_output_target_item — a per-CI result record
  6. Write Aggregate Stats to cmdb_ire_output_aggregate_stats — batch and run-level summary
⬦ Decision Point — Commit Successful?
YES → 🎉 SUCCESS. Payload Processed Successfully. The CI is live in the CMDB.
NO → Rollback Transaction — ALL database operations from steps 1–6 are reverted. The CMDB is left exactly as it was. The failure is logged for investigation. The payload does not automatically re-queue.
Why Atomicity Matters

If the CI record was updated but the relationship write failed halfway through, you would have inconsistent data — a CI that exists but is not properly linked. Atomicity guarantees the database reflects the full picture, or none of it. No half-states.

▸ Tables Involved
cmdb_ci_* cmdb_rel_ci sys_object_source cmdb_datasource_last_update cmdb_ire_output_target_item cmdb_ire_output_aggregate_stats
Section 04

The 3 Final Outcomes

Every payload that enters IRE will reach exactly one of these three destinations — no exceptions, no other possibilities.

✅ Successful Commit

The payload completed all applicable phases without issue. The CI has been created or updated in the target CMDB table. All supporting records — relationships, source tracking, output logs — have been written.

Where to see it: cmdb_ire_output_target_item with operation inserted, updated, or unchanged. Batch stats in cmdb_ire_output_aggregate_stats.

⏳ Partial Payload Stored

The payload is valid but cannot be fully processed yet — either because a dependency CI does not exist, or because INSERT_NOT_ALLOWED_FOR_SOURCE is blocking creation pending an authorised source. The payload is held in cmdb_ire_partial_payloads and will be recovered automatically when the condition resolves.

TTL: Automatically purged after 90 days if unresolved.

Not in output table: These payloads do NOT appear in cmdb_ire_output_target_item. Monitor the partial payloads table directly.

❌ Incomplete — DLQ

A fatal validation error in Phase 1. The payload was structurally invalid, referenced a non-existent CI class, or was missing required fields. Cannot be processed automatically.

Where it lives: cmdb_ire_incomplete_payloads — the Dead Letter Queue. Stores raw payload, error details, stack trace, source info, and received timestamp.

Action required: Manual review. This is not self-healing.

Section 06

Common Issues & What To Do

The five most common IRE problems, what they mean, and how to resolve them.

📦
Payload stuck in the partial table
▶
Symptom

Records accumulating in cmdb_ire_partial_payloads without resolving. Either growing by volume or not clearing after long periods.

Likely Cause

Two possibilities: (1) The dependency CI has not arrived — the source is sending child records before parent records. (2) INSERT_NOT_ALLOWED_FOR_SOURCE is set for this source/class and no authorised source has created the parent CI yet.

What To Do

Identify what dependency is missing by reviewing the payload content stored in the table — the reason code is embedded in the JSON. Use the Identification Simulation tool to run the payload and see exactly what reference is unresolvable. Investigate whether the parent CI's source integration is active and healthy. If it's an INSERT_NOT_ALLOWED scenario, check whether an authorised source has run successfully.

🔀
Duplicate task created — what now?
▶
Symptom

New records appearing in reconcile_duplicate_task. A CI update has stalled waiting for resolution.

Likely Cause

Two or more CI records exist in the CMDB with matching identification attributes. IRE found more than one match in Phase 5 and could not safely choose one.

What To Do

Open the deduplication task. Review both records side by side. Use the Duplicate CI Remediator wizard to choose which record to keep and decide how to handle attribute values from each. Do not manually delete the losing record — orphaned relationships and source tracking entries can result. Always use the remediator.

🚫
Source blocked — INSERT_NOT_ALLOWED
▶
Symptom

Records in cmdb_ire_partial_payloads with reason INSERT_NOT_ALLOWED_FOR_SOURCE. New CIs from this source are not appearing in the CMDB.

Likely Cause

A rule in cmdb_ire_data_source_rule has "Insert not allowed" checked for this source + CI class combination. The CI doesn't yet exist, so there's nothing to update — the payload is held in partial state waiting for an authorised source to create the CI first.

What To Do

If the behaviour is intentional: check whether the authorised source (e.g. Discovery) has run and successfully created the CI. Once the parent CI exists, the partial payload will be reprocessed automatically as an update. If the rule is misconfigured: navigate to the data source rule for this source + class combination and review the "Insert not allowed" setting.

🔄
Reclassification pending approval
▶
Symptom

CI class is not updating despite new payloads arriving. New records appearing in reclassification_task.

Likely Cause

A downgrade or horizontal reclassification was attempted, and system properties require manual approval before it can proceed.

What To Do

Review the open reclassification_task. Validate whether the class change is correct by checking the source data. Approve to allow the change, or reject to keep the current class. If approvals are creating a backlog, discuss reclassification property settings with your architect — some environments allow automatic upgrades while requiring human sign-off only for downgrades.

🪦
Dead Letter Queue is growing
▶
Symptom

cmdb_ire_incomplete_payloads accumulating records, particularly from a specific source.

Likely Cause

An integration is sending malformed payloads, referencing a CI class that does not exist in this environment, or missing mandatory fields. Phase 1 is failing consistently.

What To Do

Sample a few DLQ entries from the affected source. Review the error details and stack trace stored with the record. Identify the pattern — is it always the same class? The same missing field? Share the error details with the integration owner. Use the raw payload in the Identification Simulation tool to replicate and diagnose the failure safely, without touching production data.

The Short Version

IRE is ServiceNow's quality control system for CMDB data. Everything coming in must pass through it — no exceptions. It checks:

  • Is this payload valid?
  • Is this source allowed to create new records for this class?
  • Does it depend on something else that doesn't exist yet?
  • Have we seen this CI from this source before?
  • Is this CI new, existing, or a duplicate?
  • Which source gets to update which fields?
  • Has the CI type changed?
  • Commit everything — or roll everything back.

There are only 3 places a payload can end up: committed to the CMDB, held waiting for a dependency, or queued in the DLQ for investigation. Nothing is silently lost.

When You See Something Wrong

A CI not appearing, a task being created, a payload not processing — don't touch the data directly. Everything has a workflow and an audit trail. Follow the task. Raise it with your admin or ServiceNow team with the table name and record details.

Daily Monitoring Checklist

  • cmdb_ire_output_aggregate_stats — review daily for spikes in error or incomplete counts
  • cmdb_ire_incomplete_payloads — new DLQ entries need triage and integration owner notification
  • cmdb_ire_partial_payloads — watch record count for unexpected growth (dependency issues or INSERT_NOT_ALLOWED backlogs)
  • reconcile_duplicate_task — open tasks need assignment and resolution before that source can proceed
  • reclassification_task — open tasks may be silently blocking CI class updates

Your First Tool When Diagnosing a Failure

Search for "Identification Simulation" in the ServiceNow navigator. Paste the failing payload, select the source, and click Run. IRE processes the payload through its full identification logic without making any changes to the CMDB. The output shows exactly which phase it fails at and why.

Key Principle

IRE decisions are always logged. Before escalating, check cmdb_ire_output_target_item for the status and reason of the specific payload. For partial/INSERT_NOT_ALLOWED issues, check cmdb_ire_partial_payloads directly — they do not appear in the output table.

Primary Configuration Entry Points

  • CI Class Manager (search in navigator) — your central interface for all IRE rule configuration: Identification Rules, Reconciliation Rules, Inclusion Rules, Data Refresh Rules — all per CI class
  • cmdb_ire_data_source_rule — manage which source is permitted to insert new CIs for which class. Every new integration source should be evaluated here.
  • Reconciliation Rules — configure static (priority-based) and dynamic (first/last/most reported) rules. Define your authoritative source matrix before onboarding any new source.
  • Data Refresh Rules — set staleness thresholds per source. If a source goes quiet on a field for N days, a lower-priority source can step in.

After Any Identification Rule Change

Review sys_object_source for stale entries. Existing fast-pass cache entries continue routing CIs using old rule results. For significant rule changes, consider a targeted cleanup of affected class entries. Always test changes using the Identification Simulation tool before applying to production.

Testing Before Deploying

Always use the Identification Simulation tool to validate new or modified identification rules against real payload samples before applying changes to production.

Invoking IRE Programmatically

The primary API is:

IdentificationEngineScriptableApi.createOrUpdateCIEnhanced(source, payloadJSON, options)

Payload structure: JSON object with an items array. Each item contains className, values (field/value pairs), and optionally relations (relationship data) and lookup (related lookup records).

Critical — IRE Bypass Risk

⚠️ Direct Inserts Bypass IRE

If your integration does not use Service Graph Connectors or IntegrationHub ETL, it must explicitly call the IRE API to go through all 8 phases. Direct inserts into cmdb_ci_* tables via GlideRecord bypass all phases — no duplicate checking, no reconciliation rules, no source tracking. This is the most common cause of data quality issues in custom integrations.

Reading Output

  • Check cmdb_ire_output_target_item for per-CI results. Operation values: inserted, updated, unchanged, skipped, partial, incomplete
  • For INSERT_NOT_ALLOWED scenarios — check cmdb_ire_partial_payloads directly. These do NOT appear in the output table.
  • Enable IRE debug logging via system properties for full processing trace — shows every phase decision and identifier entry evaluated

Design Decisions — Make These Before Onboarding Any Source

  • Source authority matrix — for each CI class, document which source can insert and which specific fields each source owns. Build cmdb_ire_data_source_rule and reconciliation rules from this matrix. Do this first — retrofitting is costly.
  • Identification attribute strategy — prefer unique, immutable attributes (serial number, product instance ID, MAC address). Name-based identification causes false matches in dynamic environments. Use combination identifier entries for resilience.
  • Dependency ordering — design integrations to send parent CIs before child CIs. Where this isn't possible, rely on Phase 3 partial holding — but monitor the 90-day TTL closely.
  • Reclassification policy — decide upfront whether automatic class changes are acceptable. Conservative pattern: allow automatic upgrades, require human approval for downgrades and horizontal moves.
  • Fast-pass cache lifecycle — sys_object_source is a performance cache, not a permanent truth store. Include it in CMDB housekeeping. After any major data migration, integration change, or identification rule change, audit affected entries.
  • IRE bypass audit — catalogue every integration and script that writes to CMDB tables. Any that don't use the IRE API are operating outside all quality controls. This is a governance and compliance exposure in regulated industries.
  • Static vs Dynamic reconciliation — dynamic rules take precedence when both apply to the same field. Design the reconciliation strategy intentionally — a mix of both types requires careful documentation.
Section 08

Good to Know

Additional context, tools, and nuances that don't fit neatly into any single phase but are important for working effectively with IRE.

Tool

🔬 The Identification Simulation Tool

ServiceNow ships with a built-in diagnostic tool called Identification Simulation. Find it by searching "Identification Simulation" in the application navigator.

Paste a payload JSON, select a discovery source, and run it. IRE processes the payload through its full identification logic — but makes absolutely no changes to the CMDB. The output shows exactly which identifier entry matched (or didn't), which CI was found, and what the proposed outcome would be.

When to use it:

  • Diagnosing a failing integration without touching production data
  • Testing new identification rules before deploying them
  • Investigating why a CI landed in the DLQ or partial table — paste the raw payload from the record
  • Validating that a new source payload is structured correctly before go-live

This is your most valuable IRE diagnostic tool. Use it before escalating any payload-related issue.

Admin Interface

🏗️ CI Class Manager

The CI Class Manager is the primary admin interface for all IRE configuration. Access it from the application navigator by searching "CI Class Manager".

From here you configure per CI class:

  • Identification Rules and Identifier Entries (attributes, priority, lookup tables)
  • Reconciliation Rules (static and dynamic, per source)
  • Inclusion Rules (advanced eligibility filtering — see below)
  • Data Refresh Rules (staleness thresholds per source)
  • Class hierarchy and attribute definitions

This is the one interface to know if you manage CMDB data quality.

Advanced Configuration

📝 Inclusion Rules

Inclusion Rules are an optional advanced feature for Phase 5. They allow you to restrict which existing CI records are considered as potential matches during identification queries.

Without inclusion rules, IRE considers all CI records of the target class as potential matches — including decommissioned, retired, or test records. An inclusion rule lets you add conditions, such as only matching against records where operational_status = Operational.

When to Use Them

In environments where retired or test CIs share attribute values with production CIs. Without inclusion rules, a new production server with the same serial number as a decommissioned server would trigger a multi-match and create a duplicate task — even though the decommissioned record is no longer relevant. There are no out-of-the-box inclusion rules; they are optional but powerful in regulated or complex environments.

Operational Risk

⚠️ The Stale sys_object_source Caveat

The sys_object_source table is the fast-pass cache built over time as IRE successfully processes payloads. Each entry maps: this source + this native key = this CMDB CI.

The risk: If you change identification rules after this cache has been built, the existing entries continue to route using the old results. The fast-pass in Phase 4 will bypass Phase 5 entirely and bind directly to a CI that may no longer be the correct match under your new rules.

When This Becomes a Problem

  • After significant identification rule changes
  • After a CMDB data migration where CI sys_ids change
  • After decommissioning a source and its CIs
  • After merging duplicate CIs
Recommendation

When making meaningful identification rule changes, scope the affected classes and clean up corresponding sys_object_source entries. Some teams implement a scheduled maintenance job for this as part of standard CMDB hygiene processes.

Phase 6 — Deeper Look

⚡ Static vs Dynamic Reconciliation Rules

Understanding the difference between these two rule types is important for anyone configuring Phase 6.

Static Rules

Assign a fixed numeric priority to each authorised source for a given attribute or class. Lowest priority number wins — always. Simple to understand, easy to audit.

Example: SCCM priority 1, Intune priority 2. SCCM always wins on the ram field as long as its data isn't stale.

Dynamic Rules

Winner is selected based on data characteristics: First Reported, Last Reported, Most Reported, Smallest or Largest Value. Dynamic rules take precedence over static rules when both apply to the same field.

Data Refresh Rules — How Staleness Works With Static Rules

When a static rule is in effect and the primary source hasn't updated a specific field within N days, the Data Refresh Rule marks that source as stale. The next-in-priority source is then permitted to update it — temporarily taking ownership until the primary source becomes active again. This prevents a failed integration from indefinitely locking fields it is no longer updating.
