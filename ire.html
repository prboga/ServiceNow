Engine Kernel Reference

A microscopic, production-grade technical specification of the IRE execution layer, internal caching structures, state machine lifecycle, and database-level storage architecture.

Domain: com.snc.cmdb.identification Layer: Native Java Kernel Runtime: Rhino / GraalVM Scope: ServiceNow CMDB Core
§ 01

Executive Kernel Architecture

1.1 Absolute Separation of JavaScript and Java Runtime Environments

The IRE operates across two completely isolated execution environments that communicate through a strictly typed bridge. Understanding this boundary is foundational to diagnosing all IRE behavior.

The JavaScript Runtime Layer (either Mozilla Rhino for pre-Tokyo instances or GraalVM Polyglot for Tokyo+) executes all scoped and global server-side scripts. Rhino/GraalVM has no direct access to CMDB kernel internals. It cannot call native Java methods from com.snc.cmdb.identification.* directly. It operates in a sandbox with a serialized object model, where all GlideRecord-based queries are channeled through the platform's GlideDB abstraction layer — incurring full ORM overhead, ACL evaluation, business rule firing, and field transform processing per row.

The Native Java Application Layer kernel at com.snc.cmdb.identification runs as a set of privileged platform services inside the application node's JVM heap. This layer has direct JDBC-level access to the underlying database, bypasses all GlideRecord overhead including ACL checks, business rules, and display value transforms, and operates against raw column data. The IRE kernel never surfaces through any public Java API that could be called from JavaScript directly.

⚡ Bridge Mechanism
The sole sanctioned communication path from JavaScript into the IRE kernel is through the sn_cmdb.IdentificationEngineScriptableApi platform scriptable object. This class is a thin, thread-safe Java-to-Script bridge registered in the GlideScriptableAPI registry. It serializes the JavaScript argument into a typed Java object graph and hands it across the JVM boundary to the kernel dispatcher.

1.3 Thread Safety, Transaction Atomicity, and Memory-Bound Parsing

Thread Safety Model

The IRE kernel employs a per-request isolation model. Each call to dispatch() is bound to a single IREExecutionContext object that is never shared across threads. All mutable state within a single IRE execution lives exclusively inside this context object on the owning thread's call stack. No global mutable state is modified during processing. The singleton dispatcher itself is stateless beyond the thread pool reference.

The only shared, concurrently accessed structures are the IRE in-memory identifier rule cache (a ConcurrentHashMap<String, CompiledIdentifierRuleSet> keyed by class name) and the data source rule cache (a CopyOnWriteArrayList<DataSourceRule>). Both are populated lazily at first access and invalidated by a platform cache flush event emitted when the underlying cmdb_identifier or cmdb_ire_data_source_rule tables are modified.

Transaction Atomicity

The IRE kernel does not open its own JDBC transaction. It inherits and participates in the ambient GlideTransaction already established by the calling thread (whether that is an inbound REST call, a scheduled job, or an integration spoke). This means all IRE writes to cmdb_ci_*, cmdb_rel_ci, cmdb_datasource_last_update, and the output tables are included in the caller's transaction savepoint. If glide.id_engine.rollback_on_error is true, a fatal IRE error issues a ROLLBACK TO SAVEPOINT against the ambient transaction, reverting all IRE writes within that batch item without aborting the outer transaction, enabling partial-batch success semantics.

Memory-Bound Parsing — Bypassing GlideRecord Bottlenecks

The kernel's Jackson-based payload deserializer allocates the full IREPayloadGraph in the JVM heap as a structured object tree. Field lookups during Phase 1 and Phase 5 operate against in-memory HashMap structures keyed by column name, not through GlideRecord's field iterator. Class hierarchy traversal (finding parent class definitions) is performed against the platform's DBObjectCache (an in-memory replica of sys_db_object loaded at node startup), requiring zero database round-trips for schema introspection. This is the primary reason IRE throughput significantly exceeds equivalent GlideRecord-based processing pipelines.

⚠ Critical Boundary
Any customization that forces a GlideRecord query during IRE execution (e.g., a business rule on cmdb_ci that queries another table) re-enters the GlideRecord path and can introduce lock contention or deadlocks if the ambient transaction has already acquired row-level locks on the target table. This is the most common cause of IRE performance degradation in heavily customized instances.

01 Structural Validation & Class Hierarchy Discovery Validation

Upon receiving the deserialized IREPayloadGraph, the kernel immediately validates the structural integrity of each item node before any database I/O is performed.

DBObjectCache Lookup

The className field in the item (e.g., "cmdb_ci_linux_server") is submitted to the platform's DBObjectCache — an in-memory synchronized map populated from sys_db_object at node boot and updated via table change events. The cache returns a DBObjectDescriptor containing the full ancestor class chain, mandatory fields, column type descriptors, and max-length constraints. A missing class name, or a class name that resolves to a non-CMDB table (i.e., one not extending cmdb_ci), causes an immediate fatal structural error. The item exits to the DLQ (cmdb_ire_incomplete_payloads).

Mandatory Field Inquest

The DBObjectDescriptor exposes a List<ColumnDescriptor> getMandatoryColumns() method that returns all fields marked mandatory=true at any level of the inheritance chain. For each mandatory column, the kernel checks whether the payload item's values map contains a non-null, non-empty entry. Fields that fail this check are collected into a MissingFieldsViolation list. If the list is non-empty, the item status is set to REQUIRED_ATTRIBUTE_EMPTY — a recoverable error that routes to the partial payload cache rather than the DLQ (see §4).

Type Coercion Validation

Each provided field value is checked against its ColumnDescriptor.getType(). Type mismatches (e.g., a string value for an integer column that cannot be coerced) generate a TypeCoercionFailure and are treated as fatal per-field errors. The field is dropped from the write map; if it was mandatory, this cascades into a REQUIRED_ATTRIBUTE_EMPTY condition.

02 Pre-Gatekeeping / Firewall Rule Check Gatekeeping

Before any identity resolution logic begins, the kernel evaluates whether the calling data source is permitted to perform the inferred operation class (INSERT or UPDATE) on the target CI class. This prevents unauthorized discovery tools from creating or overwriting CI records in protected class namespaces.

Rule Cache Evaluation

Data source rules are cached in a CopyOnWriteArrayList<DataSourceRule> populated from cmdb_ire_data_source_rule. Each DataSourceRule object holds: source_name, cmdb_class (with wildcard support using a compiled Pattern), allow_insert (boolean), allow_update (boolean), and applies_to_subclasses (boolean). The kernel iterates this list and finds all rules where rule.matches(dataSource, className) returns true. The most specific matching rule (longest class name match) wins. Wildcard * rules serve as a global default.

INSERT_NOT_ALLOWED_FOR_SOURCE

When the matched rule has allow_insert = false and the current item has no existing CI sys_id (i.e., it would result in a CREATE), the kernel sets the item result code to INSERT_NOT_ALLOWED_FOR_SOURCE and terminates processing for that item. No partial payload entry is created. The item result is written directly to cmdb_ire_output_target_item with the blocked status. The outer batch continues processing remaining items.

Disabling the Check

Setting the system property glide.id_engine.cmdb_data_source_rule.enable to false causes the kernel to skip Phase 2 entirely, treating all sources as unconditionally permitted. This should only be used in sandboxed development environments, never in production.

03 Cache Lookback & Payload Reconstruction Cache

Phase 3 implements the partial payload recovery mechanism — the IRE's ability to stitch together a complete CI record from fragments that arrived in separate submissions over time, each of which was individually insufficient to satisfy the identifier rule's required attribute set.

Dependency Hash Computation

The kernel computes a dependency resolution key for the current item. For items with lookupEntries references (where a related CI must be identified first to populate a reference field), the key encodes the dependency CI class and its identifying attributes. This key is a deterministic SHA-256 hash of the sorted canonical form of: className + dataSource + sorted(identifyingAttributeKeys). The hash is computed in-memory using the JVM's java.security.MessageDigest without any I/O.

Index Table Query

The kernel executes a direct JDBC query (not GlideRecord) against cmdb_ire_partial_payloads_index:

SELECT sys_id, payload_table_ref, dependency_key, created_on
FROM   cmdb_ire_partial_payloads_index
WHERE  dependency_key = ?
  AND  source_name    = ?
  AND  class_name     = ?
  AND  created_on     > NOW() - INTERVAL 90 DAY;

If a matching index row is found, its payload_table_ref column contains the sys_id of the corresponding row in cmdb_ire_partial_payloads that holds the actual JSON blob.

In-Memory Merge & Cache Purge

The kernel fetches the payload_json TEXT column from cmdb_ire_partial_payloads for the referenced row. It deserializes the stored JSON blob into a transient IREPayloadItem object and performs a field-level merge with the current item in memory. Merge semantics: current item fields take precedence over stored fields for any key collision (the newer payload wins). After the merge, both the index row and the payload blob row are immediately DELETEd within the current transaction (not deferred). The merged item then continues to Phase 4 as if it were a single, complete submission.

📦 90-Day TTL
Partial payload rows older than 90 days are excluded from the lookback query above via the created_on > NOW() - INTERVAL 90 DAY predicate. A nightly scheduled cleanup job (SNC Scheduled Job: IRE Partial Payload Expiry) also issues hard DELETEs against both tables for any rows older than 90 days, preventing unbounded table growth.
04 Fast-Pass Identity Resolution Identity

Phase 4 is an optimized short-circuit that bypasses the expensive rule engine entirely when a prior registration of the source+native-key combination already exists in the identity register.

sys_object_source Direct Lookup

The kernel issues a single-row JDBC lookup against sys_object_source:

SELECT target_sys_id, target_class
FROM   sys_object_source
WHERE  source_name       = ?   -- e.g., "ServiceWatch Probe"
  AND  source_native_key = ?   -- e.g., "SN-A7F9-2241" or tool-native ID
LIMIT  1;

The source_native_key value is taken directly from the item's source_native_key field in the payload. This field must be populated by the discovery source for Fast-Pass to be applicable. If the source does not supply a source_native_key, this phase is skipped.

Cache Hit Path

On a hit, the kernel sets the item's identifiedSysId and identifiedClass on the IREExecutionContext and immediately jumps to Phase 6, bypassing Phase 5 entirely. This is the single largest performance optimization in the IRE pipeline and is the primary reason integration sources that reliably supply source_native_key values process at significantly higher throughput than those that do not.

Cache Miss Path

On a miss, the kernel does not modify any state and proceeds directly to Phase 5. The sys_object_source row will be created or updated during Phase 8 upon successful commit if the item results in a CREATE or IDENTIFIED state.

05 Identifier Rule Execution & Multi-Match Processing Rules Engine

Phase 5 is the most computationally intensive phase. It executes the configured identification rule chain to attempt to match the incoming payload item to zero, one, or multiple existing CI records.

CompiledIdentifierRuleSet Cache

The kernel checks its ConcurrentHashMap<String, CompiledIdentifierRuleSet> for the target class name. On a miss, it loads the rule set from the database: it queries cmdb_identifier for the most specific applicable rule (the one whose applies_to class is the same as or closest ancestor of the target class). The result is compiled into a CompiledIdentifierRuleSet — an immutable object containing an ordered List<CompiledIdentifierEntry> sorted by priority (ascending integer, lower = higher priority).

Rule Inheritance Chain Walk

If no cmdb_identifier row directly targets the item's class, the kernel walks up the ancestor class chain (retrieved from DBObjectCache) until it finds a matching identifier or reaches cmdb_ci. This walk is performed in-memory with no additional DB queries.

Priority Loop — cmdb_identifier_entry

For each CompiledIdentifierEntry in priority order, the kernel constructs and executes a search query:

-- Example: identifier entry with criterion fields [serial_number] on cmdb_ci_linux_server
SELECT sys_id, sys_class_name
FROM   cmdb_ci_linux_server
WHERE  serial_number = ?   -- value from payload item
  AND  sys_class_name IN ( /* applicable subclass list from DBObjectCache */ )
LIMIT  2;  -- LIMIT 2 intentional: distinguishes 0, 1, and N>1 results

The LIMIT 2 is intentional. The kernel only needs to know: zero matches (no CI found), exactly one match (identified), or more than one match (duplicate/multi-match condition). Fetching the full result set would be wasteful and is never done.

Related Entry Dependency Resolution — cmdb_related_entry

Some identifier entries specify that a field is populated by reference to a related CI (e.g., a NIC card identified by MAC address + host server serial number). These are encoded in cmdb_related_entry rows linked to the parent cmdb_identifier_entry. For each related entry, the kernel performs a recursive Phase 4/5 sub-resolution for the referenced CI type using the payload's lookupEntries graph. The resolved sys_id is substituted into the parent query's WHERE clause before execution.

Multi-Match Failure State

When a query returns more than one candidate CI sys_id for the same identifier entry, the kernel logs a duplicate audit event and blocks further processing of the item:

-- cmdb_duplicate_audit_result insert (one row per multi-match event)
INSERT INTO cmdb_duplicate_audit_result (
    source_name, class_name, identifier_entry_sys_id,
    candidate_sys_ids,   -- JSON array: ["a1b2c3...", "d4e5f6..."]
    payload_snapshot,    -- truncated JSON of the offending item
    detected_on, status
) VALUES (?, ?, ?, ?, ?, NOW(), 'open');

-- reconciliation_duplicate_task insert (actionable workflow task)
INSERT INTO reconciliation_duplicate_task (
    short_description,
    cmdb_class, source_name,
    duplicate_audit_ref,    -- FK to cmdb_duplicate_audit_result
    state, priority, assigned_to
) VALUES (
    'Duplicate CI detected: cmdb_ci_linux_server from ServiceWatch Probe',
    ?, ?, ?, 'open', 2, NULL
);

The item receives an output result code of MULTI_MATCH and is not committed to the CMDB. The outer batch continues.

06 Reconciliation & Field-Level Attribute Masking Reconciliation

Phase 6 determines the precise set of fields the current data source is authorized to write, applying field-ownership and staleness rules before any data is committed to the database.

Reconciliation Rule Loading

The kernel loads applicable rows from cmdb_reconciliation_rule for the intersection of target class and data source. Each rule specifies a field name (or wildcard), a precedence order, and an authoritative flag indicating whether the source is the single authoritative writer for that field. Rules are cached per (class, source) pair in the IREExecutionContext for the duration of the batch.

Tracking Token Lookup — cmdb_datasource_last_update

For each field in the write map, the kernel reads the tracking token from cmdb_datasource_last_update:

SELECT source_name, last_update, precedence_rank
FROM   cmdb_datasource_last_update
WHERE  ci_item_sys_id = ?       -- the identified CI's sys_id
  AND  field_name     = ?;      -- the specific column being evaluated

This row records which data source last successfully wrote this field and when. If the current source has a lower precedence rank (higher priority number = lower priority in this model) than the source recorded in the token, the field is masked — removed from the write map. The higher-precedence source retains ownership of the field value, and the current submission's value for that field is silently discarded.

Staleness Override — cmdb_data_refresh_rule

A source that would otherwise be outranked can reclaim a field if the existing token's last_update timestamp is older than the TTL configured in a matching cmdb_data_refresh_rule row. The kernel evaluates:

IF (NOW() - token.last_update) > data_refresh_rule.max_age_seconds THEN
    -- The higher-priority source's data is considered stale.
    -- Current source is permitted to write this field regardless of precedence.
    fieldWriteMap.include(fieldName, payloadValue);
ELSE
    fieldWriteMap.exclude(fieldName); -- mask: do not overwrite
END IF;

After this evaluation, the fieldWriteMap contains only the fields the current source is authorized and required to write. All subsequent phases operate only against this filtered map.

07 Reclassification Matrix Processing Reclassification

Phase 7 executes only on UPDATE paths (when an existing CI was identified). It compares the CI's current stored class against the class specified in the incoming payload and determines whether a reclassification operation is necessary and permitted.

Reclassification Delta Calculation

Using the in-memory class hierarchy from DBObjectCache, the kernel computes the relationship between currentClass and payloadClass:

UPGRADE:    payloadClass is a subclass of currentClass
            e.g., cmdb_ci_server → cmdb_ci_linux_server
            (More specific; adds specialized attributes)

DOWNGRADE:  payloadClass is a superclass of currentClass
            e.g., cmdb_ci_linux_server → cmdb_ci_server
            (Less specific; loses specialized attributes)

HORIZONTAL: payloadClass and currentClass share a common ancestor
            but neither is an ancestor of the other
            e.g., cmdb_ci_linux_server → cmdb_ci_win_server
            (Lateral switch; both are children of cmdb_ci_server)

NONE:       payloadClass == currentClass
            (No reclassification needed; Phase 7 exits immediately)

Restriction Property Checks

The kernel evaluates the following system-level restriction flags before allowing any reclassification:

glide.cmdb.reclassification.allow_downgrade  (boolean, default: true)
glide.cmdb.reclassification.allow_horizontal (boolean, default: true)
glide.cmdb.reclassification.restricted_classes (comma-delimited class list)

If the target class appears in restricted_classes, all reclassification into that class is blocked regardless of direction. If the computed delta type is DOWNGRADE and allow_downgrade is false, the reclassification is blocked. Similarly for HORIZONTAL.

cmdb_reclassification_task Generation

For permitted reclassifications, the kernel inserts a cmdb_reclassification_task row before any schema changes are applied. The task records the from-class, to-class, delta type, the triggering data source, and the CI sys_id. The actual table-level schema change (moving the row from one extended table to another) is deferred to Phase 8 as part of the atomic commit sequence.

⚠ Horizontal Reclassification Risk
Horizontal reclassification requires: (1) DELETEing the row from the source extension table, (2) INSERTing into the destination extension table, and (3) leaving the base cmdb_ci and cmdb_ci_hardware rows intact. If this operation is interrupted mid-Phase-8, orphaned extension rows can result. Ensure glide.id_engine.rollback_on_error is true in any environment processing reclassifications.
08 Atomic Transaction Commit Phase Commit

Phase 8 materializes all decisions made in Phases 1–7 into durable database writes within the ambient transaction. All SQL operations in Phase 8 are issued as a single batched statement group to the JDBC connection.

CI Table INSERT / UPDATE

-- CREATE path: new CI
INSERT INTO cmdb_ci (sys_id, sys_class_name, name, sys_created_by, ...)
VALUES (UUID(), 'cmdb_ci_linux_server', 'prod-db-01.corp.internal', 'system', ...);

-- Extended table insert (for non-base-class attributes)

Hard-deleted when consumed or when the nightly TTL cleanup job runs. Never modified in-place; consumed rows are deleted and re-inserted if an update arrives.

Status field transitions from open to resolved when the linked reconciliation_duplicate_task is closed.

Assigned to the CMDB data stewardship group or a configured assignment group. State machine: open → in_progress → resolved. cmdb_reclassification_task State Tracking Write Only Task record created before a reclassification is applied. Records the source and destination class, the reclassification type (UPGRADE, DOWNGRADE, HORIZONTAL), and the triggering source. Written in Phase 7. The task transitions to completed automatically after the Phase 8 commit succeeds. If Phase 8 fails and rolls back, the task is also rolled back within the same transaction.

Contains: batch_request_id, item_index, result_code (CREATED, UPDATED, NO_CHANGE, BLOCKED, ERROR, MULTI_MATCH), ci_sys_id (if committed), and a message string for error details. The primary output consumed by the calling integration to understand per-CI processing results.

The row is INSERTed at batch start and UPDATEd (counter increment) after each item commits or fails in Phase 8. Read by the caller's response handler after all items are processed to build the batch-level summary response.
§ 04

Deep Dive: Error Recovery & Cache Processing Mechanics

4.1 Recoverable Error Pipeline

Recoverable errors arise when an item is structurally valid and not blocked by gatekeeping, but cannot be fully processed in the current submission because of missing dependency data or empty required attributes. Rather than failing permanently, the kernel serializes the item into the partial payload cache to await a future submission that satisfies the outstanding requirements.

Error conditions classified as Recoverable:

  • MISSING_DEPENDENCY — A lookupEntry referenced CI type could not be identified; the parent CI therefore has an unresolvable reference field.
  • REQUIRED_ATTRIBUTE_EMPTY — One or more mandatory fields for the identifier rule are absent in the current payload but may arrive in a subsequent submission.
  • PARTIAL_IDENTIFIER_DATA — Some but not all fields required for the highest-priority identifier entry are present; insufficient for a reliable identity resolution.

4.2 Fatal Error Pipeline — Dead-Letter Queue & Table Rotation

Fatal errors represent payloads that are permanently unprocessable: malformed JSON that cannot be deserialized, completely absent identity metrics with no possibility of future resolution, or class names that do not exist in the CMDB schema. These items are routed to the Dead-Letter Queue implemented by cmdb_ire_incomplete_payloads.

Error conditions classified as Fatal:

  • MALFORMED_JSON — The payload string could not be parsed by the Jackson deserializer. The raw string is stored as-is (truncated to 64 KB).
  • INVALID_CLASS — The className field resolves to no entry in sys_db_object, or to a non-CMDB table.
  • NO_IDENTITY_METRICS — Zero fields in the payload correspond to any identifier entry criterion for the target class. No identifier rule can ever match this item.
  • PAYLOAD_GRAPH_CYCLE — The lookupEntries dependency graph contains a circular reference that cannot be resolved.

🔁 Why Table Rotation Instead of DELETE?
A rolling TRUNCATE strategy is architecturally superior to periodic DELETE WHERE created_on < NOW() - INTERVAL 7 DAY for DLQ workloads because: (1) TRUNCATE is a DDL operation that returns pages to the OS immediately, preventing InnoDB/MySQL tablespace bloat; (2) it is O(1) regardless of row count; (3) it does not generate individual undo log entries, avoiding transaction log pressure; and (4) it does not require a full table scan. The cost is reduced query precision — you cannot selectively retain DLQ entries older than 7 days without additional archival infrastructure.

Kernel-Level System Properties & Micro-Tuning Flags

The following system properties are evaluated by the IRE kernel at runtime. Changes to these properties take effect on the next IRE invocation without a node restart, as they are read from the platform property cache which is updated on write. Properties are set via System Definition → System Properties or via the sys_properties table directly.

Property Name
Type
Default
Micro-Tuning Impact & Behavioral Detail
glide.cmdb.logger.source.
identification_engine
String
warn

Controls the log verbosity level of the IRE kernel's internal logger (com.snc.cmdb.identification). Valid values in ascending verbosity order: error, warn, info, debug, trace.

Setting to debug causes the kernel to output to the node's logs/glide.log: each phase transition per item, cache hit/miss events for the identifier rule cache and Fast-Pass, result codes per item, and field masking decisions (which fields were masked and by which competing source).

Setting to trace additionally emits the compiled SQL statement strings for every JDBC query issued during Phases 3, 4, 5, and 6, along with the bind parameter values (WARNING: bind values may include PII such as hostnames and IP addresses). Trace-level output also logs the full in-memory merge result after Phase 3 partial payload reconstruction and the complete field write map after Phase 6 masking.

Production warning: trace level generates approximately 2–8 KB of log output per payload item. At high integration throughput (10,000+ items/minute), this will saturate disk I/O on the node's log volume and cause severe performance degradation. Use debug or trace only during targeted diagnostic windows with throttled input volume.

glide.id_engine.partial_payload.enable
Boolean
true

Master toggle for the Phase 3 partial payload cache system. When set to false, the kernel skips Phase 3 entirely — no lookback query is issued against cmdb_ire_partial_payloads_index, no partial blob is fetched or merged, and no new partial payload entries are created for recoverable errors.

Recoverable errors (MISSING_DEPENDENCY, REQUIRED_ATTRIBUTE_EMPTY) that would otherwise generate partial cache entries are instead treated as non-fatal, non-cached errors: the item is written to cmdb_ire_output_target_item with result code SKIPPED_NO_CACHE and processing continues without any cache write.

Disabling this property reduces database write volume and eliminates Phase 3 latency for integrations where all dependency data is guaranteed to arrive in a single payload (e.g., fully enriched SCCM payloads). It should be disabled with caution for integrations that legitimately rely on multi-submission dependency resolution (e.g., agentless network discovery where topology and host data arrive in separate scans).

Existing rows in the partial payload tables are not purged when this property is set to false. They will simply never be consumed.

glide.id_engine.cmdb_data_source_rule.enable
Boolean
true

Controls whether Phase 2 Pre-Gatekeeping evaluation is performed. When set to false, the kernel bypasses the entire cmdb_ire_data_source_rule evaluation, treating every data source as unconditionally permitted to INSERT and UPDATE any CI class.

The CopyOnWriteArrayList<DataSourceRule> cache is still populated at first access even when this flag is false, as the cache population code path does not check this property. The property is only evaluated at the point where the rule evaluation logic would execute within Phase 2.

Disabling this property provides a minor performance improvement (one cache list traversal is skipped per item) but eliminates a critical security boundary that prevents unauthorized discovery sources from creating CIs in protected namespaces. This flag should only be set to false in isolated development or load-testing environments where all data sources are trusted and data source rules have not been configured.

Note: Disabling this flag does not affect reconciliation precedence (Phase 6). Data source rules and reconciliation rules are independent systems. A source blocked by a data source rule would still have been subject to field masking if it had been allowed through.

glide.id_engine.rollback_on_error
Boolean
true

Controls Phase 8 transaction boundary isolation behavior when a SQL-level error occurs during the atomic commit sequence. This property governs per-item savepoint semantics within the ambient transaction.

When true (default): Before Phase 8 begins for each item, the kernel issues a SAVEPOINT ire_item_[index] against the ambient JDBC connection. If any SQL statement within the Phase 8 commit sequence fails (e.g., a unique constraint violation on cmdb_rel_ci, a foreign key violation, or a deadlock), the kernel issues ROLLBACK TO SAVEPOINT ire_item_[index] and then RELEASE SAVEPOINT ire_item_[index]. This reverts all Phase 8 writes for that item (CI tables, relationship rows, identity register, tracking tokens) without affecting the outer ambient transaction or the already-committed items in the same batch. The item receives result code ERROR in cmdb_ire_output_target_item. Batch processing continues with the next item. This enables partial-batch success semantics: 999 items in a 1000-item batch can commit even if item 500 fails.

When false: No savepoint is established. A Phase 8 SQL failure is propagated upward to the ambient transaction as an uncaught JDBC exception. The platform's transaction manager issues a full ROLLBACK of the entire ambient transaction, reverting all IRE writes across all items in the batch, all preceding business rule writes, and all caller-initiated writes within the same transaction scope. This is the all-or-nothing semantic: the entire batch either fully commits or fully rolls back. Use this setting only when absolute batch atomicity is a business requirement (e.g., financial asset CI records where partial writes would create inconsistent state).

⚠ Property Evaluation Order
System properties are read from the platform's in-memory property cache (GlideProperties), which is a node-local ConcurrentHashMap populated from sys_properties. Changes written to sys_properties via the UI or direct SQL are propagated to all nodes via the inter-node message bus with a typical latency of 1–5 seconds. During this propagation window, different nodes may evaluate different property values for the same IRE execution, which can cause transient inconsistent behavior in multi-node clusters. For critical toggles (especially rollback_on_error), verify property propagation across all active nodes before committing to a production change.
